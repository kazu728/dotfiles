# handle

計画を決めた担当が、確定した計画・全体の整合・完了に責任を持つ。ユーザーが計画を確認して実装を承認した後は、工程ごとの承認を求めず、実装・検証・独立レビュー・指摘の修正まで進める。ユーザーや別担当の変更を戻さない。

subagent のモデルと reasoning effort はユーザーの明示指定を優先する。指定がなければ、ホストが提示する用途・能力を根拠に、作業内容とユーザーの品質・速度・費用の優先度に合う設定を選ぶ。実装は必要なコーディング能力を満たす範囲で費用を考慮し、レビューは正確さを優先する。選択の根拠がない、または選択できない項目は親セッションから継承し、継承できなければホストの既定に従う。

委譲時は、選択した設定・担当範囲・結果の確認方法を簡潔に伝える。

## 1. 要求の確認と計画

要求・適用規約・既存実装と、作業ツリーの staged・unstaged・未追跡を確認し、今回の対象と既存の変更を把握する。指定された GitHub issue は本文とコメントを読む。既存情報から判断できることは調べて決め、挙動・範囲・互換性を左右する未決事項だけユーザーに確認する。

計画は次を簡潔にまとめる。

- 要求、変更後の挙動、対象範囲、受け入れ条件
- 制約、確定した仮定、検証方法
- 実装判断に必要な決定理由。却下案は再び採用するおそれがあるものだけ含める

内部の実装方法は担当が決め、公開APIやデータ形式など影響の大きい設計は計画で扱う。

計画をユーザーに提示し、その計画で実装を始めてよいという返答を待つ。承認前は調査・設計相談・計画の作成と更新に留め、実装対象の変更や subagent への実装着手指示を行わない。仕様質問への回答、一般的な「任せる」、auto mode やツール実行の許可を、計画への実装承認とみなさない。要求が明確なことや issue に計画があることだけでも省略しない。

既に確認・承認済みの具体的な計画の実装を依頼されている場合は、再承認を求めず続ける。計画確認を省略して実装まで進める明示的な委任がある場合だけ、未承認の計画でもその委任範囲で進める。

### 計画と進捗の記録

issue が指定された場合、実装を引き継ぐ・分担する場合、中断・再開する場合は、合意済み計画を保存する。正とする場所は一つに定め、以後の合意した変更も反映する。優先順は次のとおり。既存資料のどちらが正か不明な場合や、共有先にユーザーの判断が必要な場合だけ確認する。

| 条件 | 保存先 |
| --- | --- |
| 対象の issue が指定されている | その issue の本文 |
| 指定がなく、今回のタスクの計画 Markdown がある | 既存のファイル |
| どちらもない | リポジトリの規約に従い、タスクを識別できる場所に Markdown を作る |

元の要求と受け入れ条件を保持する。停止時は、判断事項・障害、現在の工程、レビュー回数、残件と次の作業を同じ保存先に記録する。issue では進捗をコメントに残す。書き戻しに失敗したら、未反映の内容と理由を報告する。

## 2. 実装と検証

担当は、残りの作業量と、説明・再調査・親による確認・手戻りを含む引き継ぎの負担を考慮して実装担当を選ぶ。会話の長さやモデル単価だけで判断せず、古い判断を実装に持ち込むおそれの解消を優先する。

| 状況 | 実装担当の選び方 |
| --- | --- |
| 前提・範囲・方針の変更が重なった、または却下案と採用案が混在している | 計画を保存し、会話履歴を継承しない新しい担当に渡す |
| 計画が明確で、残作業が小さい、または引き継ぎの負担が節約の見込みを上回る | 同じ担当が続ける |
| 計画が確定し、まとまった実装が残る | 必要な能力を持つ低コストモデルへの委譲を検討する |

引き継ぎ前に、計画と参照先だけで実装を始められることを確認する。保存先・適用規約・作業ツリーの状態と既存の変更の扱いを渡し、切り替える理由と保存先をユーザーに伝える。独立したエージェント機能が使えなければ、その制約を伝え、保存した計画を基準に同じ担当が続ける。

既存の作業を引き継ぎ、計画の範囲を実装する。一部を subagent に任せる場合は独立した作業だけを切り出す。変更に応じた検証を実行し、失敗は原因を調べて修正する。実行したコマンド・結果・未実施の確認事項を記録する。

## 3. 独立レビューと修正

実装に参加していない別担当1体に、要求との不一致・不具合・退行をレビューさせる。ホストの独立したエージェント機能を使う。deep-review は、徹底レビューを明示的に依頼され、利用可能な場合だけ使う。

- 親の会話履歴を継承させず、要求・受け入れ条件・適用規約を渡す。実装者の弁明や自己評価は渡さない。
- 比較元・対象の版・範囲を指定し、レビュアー自身に差分と必要な周辺を取得させる。未コミット変更では staged・unstaged・未追跡と、開始前からある変更の扱いを明示する。レビュー中は対象の編集を止め、外部の変更があれば影響した範囲を再確認する。
- 指摘には file:line、要求との不一致または壊れる入力・経路、検証根拠を付けさせる。レビュアーは対象を修正しない。

実装担当が指摘を裏取りする。確認できた指摘は修正・再検証し、修正箇所と影響範囲を独立した再レビューに戻す。反証できた候補は除外し、検証不能の候補は未解決として残す。「指摘なし」に含めない。

初回を含め最大4ラウンドとし、各回で独立レビュー・指摘の検証・必要な修正・再検証を行う。4回目に修正した場合は、最終変更の再レビュー未実施を記録する。独立レビューの機能がない場合や起動失敗・中断も未実施として報告し、自己確認で代替しない。

## 4. 完了

以下をすべて満たしたら、変更内容・実行した検証と結果・レビュー結果を報告して完了する。

- 受け入れ条件を満たす
- 必要な検証が成功している
- 最終変更への独立レビューが完了している
- 未解決の指摘がない

## 判断待ちと再開

仕様・範囲に新しい判断が必要、自力で解消できない障害がある、またはレビュー上限に達して完了条件を満たせない場合は、進捗を記録してユーザーに戻す。

質問は利用可能な選択式ツールを優先し、自由入力も受け付ける。ツールがなければ文章で質問する。複数の判断が相互に依存する場合は、利用可能なら grilling skill を使い、なければ依存関係の順に一問ずつ確認する。

未回答の判断に依存する作業は進めない。その場で回答を受け取れなければターンを終え、回答後は続きから再開する。毎回 `$handle` を要求せず、ホストが再呼び出しを必要とする場合だけ案内する。
