# handle

計画を決めた担当が、計画・全体の整合・完了に責任を持つ。この skill の明示的な呼び出しは、計画承認後に Goal を使って実装・検証・独立レビュー・修正を継続する指示を含む。ユーザーや別担当の変更を戻さない。

Goal の操作はホストのコマンド・ツールと権限制約に従う。ユーザー操作が必要な場合は具体的な操作を案内する。

## 計画と承認

要求・適用規約・既存実装と、作業ツリーの staged・unstaged・未追跡を確認し、今回の対象と既存の変更を把握する。指定された GitHub issue は本文とコメントを読む。既存情報から判断できることは調べて決め、挙動・範囲・互換性を左右する未決事項だけユーザーに確認する。

計画は次を簡潔にまとめる。

- 要求、変更後の挙動、対象範囲、受け入れ条件
- 制約、確定した仮定、検証方法
- 実装判断に必要な決定理由。却下案は再び採用するおそれがあるものだけ含める

内部の実装方法は担当が決め、公開APIやデータ形式など影響の大きい設計は計画で扱う。

「計画と進捗の保存」に従って計画を未承認として保存し、参照先とともにユーザーに提示する。その計画で実装を始めてよいという返答を待ち、承認を保存してから実行に進む。承認前は調査・設計相談・計画の作成と更新に留め、実装対象の変更や subagent への実装着手指示を行わない。仕様質問への回答、一般的な「任せる」、Goal の設定、auto mode やツール実行の許可を、計画への実装承認とみなさない。要求が明確なことや issue に計画があることだけでも省略しない。

既に確認・承認済みの具体的な計画の実装を依頼されている場合は、再承認を求めず続ける。計画確認を省略して実装まで進める明示的な委任がある場合だけ、その委任を記録して実行に進む。

## Goal による実行

保存した計画の参照先・対象範囲・制約・検証方法と、以下の完了条件を Goal に設定して開始する。今回の計画と条件が一致する既存の Goal は再利用する。別タスクの Goal を置き換える場合はユーザーに確認する。

Goal の完了条件は、次のすべてを満たすこと。

- 受け入れ条件を満たす
- 必要な検証が成功している
- 最終変更への独立レビューが完了している
- 未解決の指摘がない

「停止と再開」の停止条件、レビュー上限、ユーザーが指定した予算・時間制限も Goal に含める。実行中は工程ごとの承認を求めず、次の手順で完了条件を満たすまで進める。

### 実装と検証

残りの作業量と、説明・再調査・親による確認・手戻りを含む引き継ぎの負担を考慮して実装担当を選ぶ。古い判断を実装に持ち込むおそれの解消を優先する。

| 状況 | 実装担当の選び方 |
| --- | --- |
| 前提・範囲・方針の変更が重なった、または却下案と採用案が混在している | 保存した計画を、会話履歴を継承しない新しい担当に渡す |
| 計画が明確で、残作業が小さい、または引き継ぎの負担が節約の見込みを上回る | 同じ担当が続ける |
| 計画が確定し、まとまった実装が残る | 必要な能力を持つ低コストモデルへの委譲を検討する |

subagent のモデルと reasoning effort はユーザーの明示指定を優先する。指定がなければ、ホストが提示する用途・能力を根拠に、作業内容とユーザーの品質・速度・費用の優先度に合う設定を選ぶ。実装は必要なコーディング能力を満たす範囲で費用を考慮し、レビューは正確さを優先する。選択の根拠がない、または選択できない項目は親セッションから継承し、継承できなければホストの既定に従う。

委譲前に、保存した計画と参照先だけで実装を始められることを確認する。適用規約・作業ツリーの状態・既存の変更の扱い・担当範囲・結果の確認方法を渡す。選択した設定・切り替える理由・計画の参照先をユーザーに伝える。独立したエージェント機能が使えなければ、その制約を伝え、同じ担当が続ける。一部を任せる場合は独立した作業だけを切り出す。

計画の範囲を実装し、変更に応じた検証を実行する。失敗は原因を調べて修正する。実行したコマンド・結果・未実施の確認事項を記録する。

### 独立レビューと修正

実装に参加していない別担当1体に、要求との不一致・不具合・退行をレビューさせる。ホストの独立したエージェント機能を使う。deep-review は、徹底レビューを明示的に依頼され、利用可能な場合だけ使う。

- 親の会話履歴を継承させず、要求・受け入れ条件・適用規約を渡す。実装者の弁明や自己評価は渡さない。
- 比較元・対象の版・範囲を指定し、レビュアー自身に差分と必要な周辺を取得させる。未コミット変更では staged・unstaged・未追跡と、開始前からある変更の扱いを明示する。レビュー中は対象の編集を止め、外部の変更があれば影響した範囲を再確認する。
- 指摘には file:line、要求との不一致または壊れる入力・経路、検証根拠を付けさせる。レビュアーは対象を修正しない。

実装担当が指摘を裏取りし、確認できた指摘は修正・再検証する。反証できた候補は除外し、検証不能の候補は未解決として残す。「指摘なし」に含めない。

独立レビューは初回を含め最大2ラウンドとする。1回目に修正した場合は、修正箇所と影響範囲を再レビューさせる。2回目に修正した場合は、最終変更への再レビューが未実施であることを記録し、「停止と再開」に従う。独立レビューの機能がない場合や起動失敗・中断も未実施として報告し、自己確認で代替しない。

### 完了

完了条件を満たしたことを証拠で確認する。Goal の評価に必要な検証結果・レビュー結果を会話にも示し、ホストの仕組みに従って達成を確定する。変更内容・実行した検証と結果・レビュー結果を報告する。

## 停止と再開

次の場合は進捗を保存し、Goal の自動継続を止めてユーザーに戻す。

- 計画の実装承認や、仕様・範囲の新しい判断を待っている
- 自力で解消できない障害がある
- レビュー上限に達して完了条件を満たせない
- 予算・時間制限に達した

停止は未完了として報告し、タスクの完了や Goal の達成として扱わない。未回答の判断に依存する作業は進めない。その場で回答を受け取れなければターンを終える。

質問は利用可能な選択式ツールを優先し、自由入力も受け付ける。ツールがなければ文章で質問する。目的・範囲・方針がまだ固まっておらず、対話しながら決める必要がある場合は、利用可能なら grilling skill を使い、なければ一問ずつ確認する。

回答や再開の指示を受けたら、保存した計画・進捗と Goal を確認する。停止条件が解消していれば、ホストの仕組みに従って未完了の工程から再開する。毎回 `$handle` を要求せず、ホストが再呼び出しを必要とする場合だけ案内する。

## 計画と進捗の保存

計画と進捗の参照先は一つに定め、元の要求と受け入れ条件を保持し、合意した変更を反映する。保存先の優先順は次のとおり。既存資料のどちらが正か不明な場合や、共有先にユーザーの判断が必要な場合だけ確認する。

| 条件 | 保存先 |
| --- | --- |
| 対象の issue が指定されている | その issue の本文 |
| 指定がなく、今回のタスクの計画 Markdown がある | 既存のファイル |
| どちらもない | リポジトリの規約に従い、タスクを識別できる場所に Markdown を作る |

承認状態、Goal の状態、現在の工程、レビュー回数、検証結果、未確認事項、判断事項・障害、残件と次の作業を記録する。issue では計画を本文、進捗をコメントに残す。書き戻しに失敗したら、未反映の内容と理由を報告する。
