# handle

明示的に指定された実装タスクの回し方。レビューの観点は既存 skill に任せ、この skill は順序と停止条件だけを持つ。

人間に判断を委ねる箇所 — §1 の質問と承認、§2 の逸脱申告、§5 のエスカレーション — はどれも、委ねたら手を止める。ターン内で答えが返る手段（選択肢を出す質問、plan mode の承認）があればそれを使い、無ければ次の返答にも `$handle` を含めるよう依頼してからターンを終えて待つ。判断が返らないまま次のターンが始まったら、仮定で埋めずに、何を待っているかを再掲してまた止まる。判断を委ね返されたときも同じ。

ARGUMENTS に GitHub issue 番号があれば、その issue（本文とコメント）を対象タスクとする。

## 1. 計画

計画には次を書く。

- 自分で決めた仮定 — コード・慣習・docs から判断したもの
- 変えないもの
- 完了したと言うための検証方法

プロダクトの挙動、スコープ境界と非目標、エラーやエッジケースの扱い、データの移行・互換性 — 手元の文脈から推測できない判断が残っているなら、仮定で埋めずに聞く。そのまま聞くか grilling で詰めるかは、聞く前に選ばせる。

計画が終わったかは自分で判定しない。人間の承認だけが §2 に進む条件になる。

- 計画がまとまったら承認を求め、ターンを終えて返答を待つ。plan mode が使える環境なら EnterPlanMode で計画し、承認は ExitPlanMode で取る
- issue 本文に計画があることは承認の証拠にならない。承認は毎回このセッションで取る
- 承認を待ってブロックしない

issue 起点なら、計画を issue 本文に反映する。次にその issue を読む人（無人セッションを含む）が計画を再構築せずに済む状態にする。

## 2. 実装

始める前に作業ツリーの差分を見る。前のセッションが実装した範囲があれば、やり直さず続きから実装する。

計画の範囲だけを実装する。計画に無い変更が必要になったら、やる前に判断を仰ぐ。

## 3. 検証

変更面に応じた検証を実際に走らせ、何を走らせて何が通ったかを報告する。走らせられないものは理由を言う。走っていない検証を「たぶん通る」で埋めない。

## 4. 独立レビュー

fresh subagent に実行させる。日常は /code-review high、徹底時は deep-review。

- 差分は subagent 自身に取得させる。対象の指定（未コミット差分、HEAD からの差分など）だけを渡し、差分の切り出しを実装側でしない
- 実装意図・弁明・「ここは意図的」を渡さない

## 5. 収束

検証を通った指摘は握りつぶさず、提示で止めずに main セッションで直す。直したら再レビューし、指摘が無くなったら終える。

往復は main セッションが数えて4ラウンドを上限とし、達したら残った指摘と経緯を添えて人間に判断を返す。issue 起点ならその内容を issue にコメントする。
