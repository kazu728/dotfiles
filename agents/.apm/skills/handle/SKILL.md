# handle

計画を決めた担当が、同じ会話で実装から完了まで責任を持つ。計画への合意後は、工程ごとの承認を求めず、検証とレビュー指摘の修正まで進める。

## 1. 要求の確認と計画

要求、適用規約、既存実装、作業ツリーの staged・unstaged・未追跡ファイルを確認し、今回の対象と既存の変更を把握する。GitHub issue が指定された場合は、その本文とコメントも読む。

要求の曖昧さは、ユーザーに影響する選択が未決かどうかで判断する。

- 変更後の挙動・対象範囲・受け入れ条件を定められるなら、計画を短く示す。
- 不足する情報を既存コード・規約・合意済みの内容から確定できるなら、調べて判断する。
- 複数の解釈が残り、選択で挙動・範囲・互換性が変わるなら確認する。単独の判断は直接質問する。複数の判断が相互に依存する場合は、利用可能なら grilling skill を使い、なければ依存関係の順に一問ずつ確認する。

計画には、変更後の挙動・対象範囲・受け入れ条件・検証方法・重要な制約と、判断した仮定を含める。内部の実装方法は担当が決め、公開APIやデータ形式など影響の大きい設計は計画で扱う。

計画への合意が未取得なら確認し、回答を待つ。既に合意した計画があれば引き継いで実装から始める。「任せる」などの委任を受けた場合は、委任された範囲の判断を行い、方針を示して進める。要求が明確なことや issue に計画があることだけを、合意・委任の根拠にしない。

## 2. 実装と検証

既存の作業を引き継ぎ、計画の範囲を実装する。独立して進められる作業だけ subagent に任せ、全体の整合と完了は実装担当が確認する。goal の利用や実装作業の委譲は必須にしない。

変更に応じた検証を実行し、失敗したら原因を調べて修正する。実行したコマンドと結果、未実施の確認事項を記録する。検証や後片付けで、ユーザーや別担当の変更を戻さない。

## 3. 独立レビュー

実装に参加していない別担当1体に、要求との不一致・不具合・退行をレビューさせる。ホストの独立したエージェント機能を使い、モデルはホストの既定またはセッションの選択を尊重する。deep-review は、徹底レビューを明示的に依頼され、利用可能な場合だけ使う。

- 親の会話履歴を継承させず、要求・受け入れ条件・適用規約を渡す。実装者の弁明や自己評価は渡さない。
- 比較元・対象の版・範囲を指定し、レビュアー自身に差分と必要な周辺を取得させる。未コミット変更では staged・unstaged・未追跡と、開始前からある変更の扱いを明示する。レビュー中は対象の編集を止め、外部の変更があれば影響した範囲を再確認する。
- 指摘には file:line、要求との不一致または壊れる入力・経路、検証根拠を付けさせる。レビュアーは対象を修正しない。

結果の受け渡しにはホストの標準機能を使う。独立レビューの機能がない場合、起動失敗や中断の場合は未実施として報告し、自己確認で代替して完了扱いにしない。

## 4. 修正と完了

実装担当が指摘を裏取りする。確認できた指摘は修正し、影響範囲を再検証して独立した再レビューに進む。反証できた候補は除外し、検証不能の候補は未解決として残す。未解決を「指摘なし」に含めない。

初回を1回目として、レビューは最大4ラウンドとする。1ラウンドは独立レビュー、指摘の検証、必要な修正、修正後の検証まで。次のラウンドでは修正箇所と影響範囲をレビューする。4回目に修正した場合は、再レビュー未実施であることを残す。

受け入れ条件を満たし、必要な検証が成功し、最終変更への独立レビューが完了し、未解決の指摘がなくなったら完了とする。変更内容、実行した検証と結果、レビュー結果を報告する。

## 判断待ちと再開

仕様や範囲に新しい判断が必要な場合、自力で解消できない障害がある場合、レビュー上限に達して未解決が残る場合はユーザーに戻す。停止時には、判断事項または障害、合意済み計画、現在の工程、レビュー回数、残件と次の作業を残す。

未回答の判断に依存する作業は進めない。利用可能な質問手段で確認し、その場で回答を受け取れなければターンを終える。同じタスクへの回答では続きから再開し、毎回 `$handle` を要求しない。ホストの制約で再呼び出しが必要な場合だけ案内する。

## GitHub issue が指定された場合

元の要求と受け入れ条件を保持して、合意済み計画を issue 本文に追記・更新する。上限到達時は、残件と再開に必要な判断を issue にコメントする。書き戻しに失敗した場合は、反映できていない内容と理由を報告する。
