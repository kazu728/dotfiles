# adversarial-review

実装の意図や「動くはず」という前提に依存せず、コードの実際の挙動から欠陥を探す。

## 対象の決め方

依頼・呼び出し元の範囲、比較元、版を優先する。未指定なら未コミット変更（追跡ファイルの最終状態と未追跡）を対象にし、変更がなければブランチ差分を見る。範囲や比較元が一意に決まらなければ確認する。全体レビューは明示された場合だけ行う。

対象の取得では、次を守る。

- staged は index、PR は base と head、ブランチは基準ブランチとの比較を使い、無関係な作業ツリーの変更を含めない。
- 未追跡はディレクトリ内まで列挙して直接読む。対象の取得で index を変更しない。
- staged と unstaged が相殺し、コミット予定と最終状態のどちらを見るか不明なら確認する。
- Git の比較では非 Git と初回コミット前を区別する。後者は対象ファイルを新規として扱うか確認する。ファイル全体を読むだけなら Git は不要。

比較失敗は失敗として報告する。差分レビューで、差分も対象の未追跡ファイルもなければ対象なしとして終え、別の範囲へ広げない。レビュー中に対象が変わったら、指摘の位置と再現性を再確認する。

## 手順

下記の観点で、壊れる入力・経路を探す。差分だけで判断できないものは、呼び出し側・周辺まで読んで契約を確かめる。

## 観点

- **ライフタイム / 資源** — use-after-free、二重解放、非同期解放と drop の順序、リーク。
- **境界・数値** — 境界値、負値、オーバーフロー / アンダーフロー、ゼロ除算、丸め方向。
- **エラーパス** — 失敗時・部分失敗時の状態、握り潰し、途中終了でのリソース残留。
- **並行性** — データ競合、デッドロック、前提が崩れる割り込み。
- **評価順序・副作用** — 正格 / 遅延評価の取り違え、短絡の有無、副作用の順序。
- **契約違反** — 呼び出し側の前提（null 非許容・呼び出し順・不変条件）を破る変更。
- **退行** — 既存の入力で挙動が変わる箇所。

## 出力の作法

- 各指摘は `file:line` と「どの入力・経路で、なぜ壊れるか」を必須にする。この2つを書けない指摘は出さない。
- recall 重視だが、経路を示せない当てずっぽうは出さない。ひねり出さない。
- 良い点は列挙せず、問題がなければ「指摘なし」と書く。
- 対象は修正しない。修正方針は1行添えてよい。
