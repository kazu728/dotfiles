# adversarial-review

実装の意図や「動くはず」という前提に依存せず、コードの実際の挙動から欠陥を探す。
指摘するだけ。修正はしない（頼まれたら別途行う）。

## 対象の決め方

範囲・比較元・版は、依頼・呼び出し元の指定に従う。指定がなければ次の順で決める。

1. 未コミット変更（追跡ファイルの最終状態と未追跡）があれば、それを対象にする。
2. なければ、基準ブランチとの差分を対象にする。
3. 差分がないか基準ブランチがなければ、対象なしとして終える。

ファイル単位や全体は、明示された場合だけレビューする。このときは Git を使わずに読んでよい。

対象は次のものから読み、無関係な作業ツリーの変更を含めない。取得で index を変更しない。

| 対象 | 読むもの |
|---|---|
| staged | index |
| PR | base と head の比較 |
| ブランチ | 基準ブランチとの比較 |
| 未追跡 | ディレクトリ内まで列挙したファイル |

次の場合はレビューを始めない。自分で範囲を選んだり、別の範囲へ広げたりしない。

| 状況 | 動作 |
|---|---|
| 比較元が一意に決まらない（上流ブランチも origin/HEAD もなく、候補が複数ある） | 依頼元に質問して回答を待つ |
| staged と unstaged が相殺し、コミット予定と最終状態のどちらを見るか依頼から分からない | 依頼元に質問して回答を待つ |
| 初回コミット前で比較元がない | 対象ファイルを新規として扱うか質問して回答を待つ |
| 指定された比較元が存在しない、非 Git で差分を取れない | 比較失敗として報告する |
| 指定された範囲に差分がない | 対象なしとして終える |

レビュー中に対象が変わったら、指摘の位置と再現性を確かめ直す。

## 手順

下記の観点で、壊れる入力・経路を探す。差分だけで判断できないものは、呼び出し側・周辺まで読んで契約を確かめる。

## 観点

- **ライフタイム / 資源** — use-after-free、二重解放、非同期解放と drop の順序、リーク。
- **境界・数値** — 境界値、負値、オーバーフロー / アンダーフロー、ゼロ除算、丸め方向。
- **エラーパス** — 失敗時・部分失敗時の状態、握り潰し、途中終了でのリソース残留。
- **並行性** — データ競合、デッドロック、前提が崩れる割り込み。
- **評価順序・副作用** — 正格 / 遅延評価の取り違え、短絡の有無、副作用の順序。
- **契約違反** — 呼び出し側の前提（null 非許容・呼び出し順・不変条件）を破る変更。
- **退行** — 既存の入力で挙動が変わる箇所。

## 出力の作法

- 各指摘は `file:line` と「どの入力・経路で、なぜ壊れるか」を必須にする。この2つを書けない指摘は出さない。
- recall 重視だが、経路を示せない当てずっぽうは出さない。ひねり出さない。
- 良い点は列挙せず、問題がなければ「指摘なし」と書く。
- 修正方針は1行添えてよい。
