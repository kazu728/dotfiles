# prune-review

既存コードを厳し目にレビューし、削れるもの・歪んでいる構造を指摘する。
判断は、適用される規約（AGENTS.md 等）とユーザーの明示要求を優先し、その範囲内で、ツールのデフォルト挙動と1から設計した構造を基準に行う。
指摘するだけ。修正はしない（頼まれたら別途行う）。

## 対象の決め方

範囲・比較元・版は、依頼・呼び出し元の指定に従う。指定がなければ次の順で決める。

1. 未コミット変更（追跡ファイルの最終状態と未追跡）があれば、それを対象にする。
2. なければ、基準ブランチとの差分を対象にする。
3. 差分がないか基準ブランチがなければ、対象なしとして終える。

ファイル単位や全体は、明示された場合だけレビューする。このときは Git を使わずに読んでよい。

対象は次のものから読み、無関係な作業ツリーの変更を含めない。取得で index を変更しない。

| 対象 | 読むもの |
|---|---|
| staged | index |
| PR | base と head の比較 |
| ブランチ | 基準ブランチとの比較 |
| 未追跡 | ディレクトリ内まで列挙したファイル |

次の場合はレビューを始めない。自分で範囲を選んだり、別の範囲へ広げたりしない。

| 状況 | 動作 |
|---|---|
| 比較元が一意に決まらない（上流ブランチも origin/HEAD もなく、候補が複数ある） | 依頼元に質問して回答を待つ |
| staged と unstaged が相殺し、コミット予定と最終状態のどちらを見るか依頼から分からない | 依頼元に質問して回答を待つ |
| 初回コミット前で比較元がない | 対象ファイルを新規として扱うか質問して回答を待つ |
| 指定された比較元が存在しない、非 Git で差分を取れない | 比較失敗として報告する |
| 指定された範囲に差分がない | 対象なしとして終える |

レビュー中に対象が変わったら、指摘の位置と再現性を確かめ直す。

## 手順

1. 下記の観点で精査する。差分だけでは是非を判断できない指摘（必要性・1から設計したらどうか）は、差分に閉じず周辺ファイルまで読んで判断する。
2. 観点ごとに、該当箇所を `file:line` で引用して指摘を返す。

## 観点

容赦なく見る。良い点の列挙はしない。問題だけ挙げる。

- **全部必要か** — 各要素の存在理由を疑う。設定はツールのデフォルト挙動で足りるなら上書きを削る。「無くても動く」ではなく、要求・観測可能な挙動・運用上の目的を維持したまま削れるかで判断する。
- **継ぎ足しの歪み** — 論理的凝集の継ぎ足しで歪んだ構造を見つける。「1から設計したらこの形になるか」を基準に、ならない箇所を挙げる。
- **過剰・冗長** — 消せるコード、重複、分けすぎ／まとめすぎ。
- **残骸** — 使われていない・削除済み対象の残り、宙に浮いた配線。

## 出力の作法

- 問題が無ければ「指摘なし」と書く。ひねり出さない。
- 各指摘は `file:line` の引用とセットにする。引用できない指摘は書かない。
- 修正方針は1行添えてよいが、コードの書き換えはしない。
