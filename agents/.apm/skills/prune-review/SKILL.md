# prune-review

既存コードを厳し目にレビューし、削れるもの・歪んでいる構造を指摘する。
判断は、適用される規約（AGENTS.md 等）とユーザーの明示要求を優先し、その範囲内で、ツールのデフォルト挙動と1から設計した構造を基準に行う。
指摘するだけ。修正はしない（頼まれたら別途行う）。

## 対象の決め方

依頼・呼び出し元の範囲、比較元、版を優先する。未指定なら未コミット変更（追跡ファイルの最終状態と未追跡）を対象にし、変更がなければブランチ差分を見る。範囲や比較元が一意に決まらなければ確認する。全体レビューは明示された場合だけ行う。

対象の取得では、次を守る。

- staged は index、PR は base と head、ブランチは基準ブランチとの比較を使い、無関係な作業ツリーの変更を含めない。
- 未追跡はディレクトリ内まで列挙して直接読む。対象の取得で index を変更しない。
- staged と unstaged が相殺し、コミット予定と最終状態のどちらを見るか不明なら確認する。
- Git の比較では非 Git と初回コミット前を区別する。後者は対象ファイルを新規として扱うか確認する。ファイル全体を読むだけなら Git は不要。

比較失敗は失敗として報告する。差分レビューで、差分も対象の未追跡ファイルもなければ対象なしとして終え、別の範囲へ広げない。レビュー中に対象が変わったら、指摘の位置と再現性を再確認する。

## 手順

1. 下記の観点で精査する。差分だけでは是非を判断できない指摘（必要性・1から設計したらどうか）は、差分に閉じず周辺ファイルまで読んで判断する。
2. 観点ごとに、該当箇所を `file:line` で引用して指摘を返す。

## 観点

容赦なく見る。良い点の列挙はしない。問題だけ挙げる。

- **全部必要か** — 各要素の存在理由を疑う。設定はツールのデフォルト挙動で足りるなら上書きを削る。「無くても動く」ではなく、要求・観測可能な挙動・運用上の目的を維持したまま削れるかで判断する。
- **継ぎ足しの歪み** — 論理的凝集の継ぎ足しで歪んだ構造を見つける。「1から設計したらこの形になるか」を基準に、ならない箇所を挙げる。
- **過剰・冗長** — 消せるコード、重複、分けすぎ／まとめすぎ。
- **残骸** — 使われていない・削除済み対象の残り、宙に浮いた配線。

## 出力の作法

- 問題が無ければ「指摘なし」と書く。ひねり出さない。
- 各指摘は `file:line` の引用とセットにする。引用できない指摘は書かない。
- 修正方針は1行添えてよいが、コードの書き換えはしない。
