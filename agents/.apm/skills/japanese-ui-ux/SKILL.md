# 日本語のUI・UX

利用者が画面を理解し、操作の結果を予測し、迷わず目的を達成できるように設計する。SmartHRとデジタル庁の公開ガイドを参考に、日本語のプロダクトUIに使う判断基準をまとめたSkill。

## 判断の前提

- 対象の利用者、達成したい作業、現在の画面・仕様を把握する。業務用語、権限、保存・公開・削除の意味は既存の仕様から確認する。
- ユーザーの指定と既存プロダクトのコンポーネント、用語、表記、トーンを優先する。使いにくさやアクセシビリティ上の問題があれば、その影響を根拠に改善する。
- 参照元のブランドカラー、フォント、コンポーネント名、社内用語を一律に導入しない。既存の部品や標準のHTMLで要件を満たせるなら、その挙動を使う。
- 文言を仕様と一致させる。原因、処理の完了、取り消し・再試行の可否が不明なときは断定せず、判断に必要な仕様を確認する。

## 必要な資料を読む

- ラベル、説明、ボタン、リンク、エラー、状態通知の文言を扱うときは [日本語UXライティング](references/ux-writing.md) を読む。
- 画面構成、操作導線、フォーム、確認、アクセシビリティを扱うときは [UIと操作の設計](references/ui-patterns.md) を読む。

依頼に関係する資料だけを読む。このSkillは画面内の体験を扱う。技術文書や広告コピーには、それぞれの文章規範を使う。

## 設計・実装・レビュー

画面単体の見栄えに加え、操作の入口から完了までを確認する。対象の機能に関係する読み込み中、入力不備、通信失敗、データなし、権限不足の状態を見分け、次にできる操作を整える。

レビューでは、作業を完了できない問題、誤操作や情報損失につながる問題を優先する。指摘は具体的な箇所、利用者への影響、修正案を結び付け、好みと不具合を区別する。文言だけの依頼から画面全体の改修へ広げない。

変更に応じて実際の表示・操作を確かめる。文言の差し替えなら周辺の意味と表示の収まり、フォームやダイアログならキーボード操作とフォーカス、レイアウトなら狭い画面や文字拡大を確認する。日本語入力に触れた場合はIME変換中の挙動も確認する。

静的なコードや画像だけで確認した事項と、実機で操作した事項を分けて報告する。アクセシビリティ規格への適合や使いやすさを、未実施の検証で保証しない。
