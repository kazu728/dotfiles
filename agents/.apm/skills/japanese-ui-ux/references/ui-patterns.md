# UIと操作の設計

## 画面と導線

- 見出し、情報のまとまり、操作の位置で、現在地と次の作業を示す。視覚上の並びとDOM・読み上げ・フォーカスの順序を対応させる。
- 主となる操作を見分けられるようにし、戻る・中止・危険な操作との違いを表す。すべてのボタンを強調して優先度を失わせない。
- リンクは移動、ボタンは操作に使い、既存コンポーネントやネイティブHTMLの意味と挙動を保つ。見た目だけの要素にクリック処理を付けて操作部品を作り直さない。
- 補足は必要な場所に置く。短い説明はサポートテキスト、長い補足は開閉できる領域などを検討し、通常の完了通知や補足だけでモーダルを開かない。

## フォームと日本語入力

- ラベルと入力欄、説明とエラーをプログラム上も関連付ける。関連する選択肢にはグループの名前を付ける。
- 適切な入力型、`autocomplete`、`inputmode`で入力を助ける。コピー・貼り付けやパスワード管理を妨げず、メールアドレスを不必要に分割しない。
- IME変換中のEnterで送信しない。変換途中の文字列に確定後の検証をかけたり、入力中の整形でカーソルや未確定文字を壊したりしない。
- 文字数制限で貼り付けやかな漢字変換が途中で切れないかを確認する。切り捨てより、制約の事前説明と超過時の検証を検討する。既存の制約を変更する場合は保存側の仕様も確認する。
- 入力・フォーカスだけで予期せぬ送信、画面遷移、フォーカス移動を起こさない。連動して表示が変わる場合は、その関係がわかるようにする。
- エラーは色だけに頼らず、該当欄の近くに示す。`aria-invalid`や`aria-describedby`など、利用中の部品が提供する仕組みで関連付ける。
- フィールドごとのエラーに一律に`aria-live`や`role="alert"`を付けない。入力中の割り込みや重複読み上げを避ける。送信時のエラー要約へのフォーカスと、非同期の処理結果通知は別に検討する。
- 無効な操作には理由と有効にする方法がわかる説明を置く。`disabled`でフォーカスできなくなる影響を考慮し、エラーを知る機会まで失わせない。

## 確認とダイアログ

- UI上の確認は、取り消しが難しい操作、影響の大きい一括処理などで検討する。簡単に戻せる日常操作に、機械的に確認を追加しない。
- 確認には対象の名称・件数、関連する影響、元に戻せるかを示す。実行ボタンにも操作を明記し、中止する方法を用意する。
- 確認ダイアログだけで誤操作を防ごうとせず、対象の選び方、危険な操作の配置、実装済みの取り消し・復元手段も検討する。
- モーダル外の情報を参照して判断する作業や、長い入力には通常の画面を検討する。既存の短い編集ダイアログまで一律に置き換えず、判断材料の不足や多重表示の問題から評価する。
- モーダルを使う場合は既存のダイアログ部品を優先する。開いた時の適切なフォーカス、内部での操作、閉じた後の戻り先、キーボードでの中止を確認する。閉じる操作が実行扱いにならないようにする。

## 見やすさと操作可能性

- 文字、操作部品、フォーカス表示のコントラストを確認し、選択・エラー・状態を色だけで伝えない。
- キーボードで必要な操作に到達でき、フォーカスが見えて、固定ヘッダーなどに隠れないようにする。正の`tabindex`で順序をつぎはぎしない。
- タップできる範囲と隣接する操作との間隔を確保する。採用する規格の要件と例外を確認し、デザインシステムの推奨サイズを一律の適合基準と呼ばない。
- 日本語の長いラベル、狭い画面、文字の拡大で、本文や操作が隠れないかを確認する。固定の高さ、過度な改行禁止、省略表示で判断に必要な情報を失わせない。
- 必須の説明や操作をホバーだけに置かない。ツールチップを使う場合はキーボードやタッチでのアクセスも確認する。
