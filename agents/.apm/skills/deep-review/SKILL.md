# deep-review

徹底レビューの対象確定、観点別レビュー、別担当による候補検証、結果報告を行う。通常の独立レビューへの追加として使い、レビュー対象は修正しない。

## 1. 対象の確定

親が要求・受け入れ条件・適用規約を確認し、依頼から PR・ブランチ・staged・未コミット変更・ファイル全体のどれを対象にするか決める。パス指定が差分かファイル全体かも含め、判断できなければ確認する。

- 比較元はユーザー指定または PR の base を優先し、なければ利用可能な基準ブランチを確認する。比較方法と、比較元・対象の commit を記録する。
- 未コミット変更では staged・unstaged・未追跡を確認し、対象にする状態と既存変更の扱いを明示する。staged と unstaged は別々に確認し、相殺される変更を見落とさない。HEAD がない場合は初回コミット前として扱う。
- ブランチレビューを無関係な未コミット変更の有無で切り替えない。比較の失敗を差分なしと扱わず、差分なしからリポジトリ全体へ広げない。

全担当が同じ版・範囲を取得できるよう、比較元・対象の版・パス・取得方法を渡す。未コミット変更は index と作業ツリーの内容を識別できる記録またはスナップショットを用い、レビュー中は編集を止める。外部の変更を検知したら対象を再確定し、影響した範囲のレビューと候補検証をやり直す。異なる版の結果を混ぜない。

## 2. 観点別レビュー

対象に必要な観点を選び、観点ごとに実装に参加していない別担当を起動する。ホストの独立したエージェント機能を使い、同時実行枠を超える担当は順次起動する。モデルはホストの既定またはセッションの選択を尊重する。

- 正しさ・契約整合性・退行：要求と実際の挙動を照合する。コードに加え、設定や文書も対象にする。
- prune-review：要求・観測可能な挙動・運用上の目的を維持したまま削れるか、構造に歪みがないかを確認する。
- adversarial-review：境界値、エラーパス、資源管理、並行性などから壊れる入力・経路を探す。
- セキュリティ：攻撃者が制御できる入力、信頼境界、認証・権限、秘密情報・ログ、暗号・乱数、デシリアライズ、シェル補間、パス・クエリ・テンプレート生成、ネットワーク・Web 境界、依存関係・lockfile に関わる変更で追加する。メモリ安全性・競合・リソース枯渇は、攻撃経路またはセキュリティへの影響を具体的に示せる場合に扱う。

該当する skill が利用可能ならその観点を使い、なければ上記の観点を直接依頼する。対象選択は親の指定を使い、個別 skill の既定の対象選択で上書きしない。

各担当には親の会話履歴を継承させず、要求・受け入れ条件・適用規約・対象の指定・担当する観点を渡す。実装者の弁明や自己評価、他のレビュー担当の候補は渡さない。差分の一部を切り出すのではなく、担当自身に対象と契約の確認に必要な周辺を取得させる。相互依存しない読み取り・検索はまとめて行う。

各担当は候補ごとに `file:line`、要求との不一致・壊れる入力や経路・不要と判断する根拠、検証で確認すべき対象を返す。探索経過や良い点の列挙は不要で、候補数に上限は設けない。未確認の範囲や実行上の障害があれば、候補なしと区別して返す。

## 3. 別担当による候補検証

候補がなければ検証を省略する。同一の根本原因と実行経路に属する候補を重複排除し、関連する file・symbol・call path ごとにまとめる。実装にも観点別レビューにも参加していない新しい担当へ、同じ要求・規約・対象の指定と、候補・確認対象を渡す。ここでも親の会話履歴は継承させない。依存領域が独立している場合やコンテキスト上限に達する場合だけ検証担当を分ける。

- 正しさ・セキュリティの候補は、要求と実際のコードパス・設定・文書を照合し、必要なら既存テストや再現コードを実行する。
- 過剰・冗長・残骸の候補は、使用箇所、ツールのデフォルト挙動、運用上の目的を調べる。

検証担当は各候補を、根拠を確認できた指摘、反証できた候補、検証不能の候補に分けて理由を返す。依存不足・環境制約・情報不足で裏取りできない候補を、反証済みとして落とさない。

## 4. 結果と未完了の扱い

レビューした版・範囲と観点を示し、確定した指摘を `file:line` と検証根拠つきで報告する。反証して除外した候補は必要なものだけ簡潔に説明し、検証不能の候補・未実施の観点は理由と残る確認事項を示す。

独立した担当を起動できない場合や、起動失敗・中断・結果の欠落があれば、そのレビューまたは検証を未実施として扱う。親による再確認で独立レビュー済みとしない。選んだ観点のレビューと全候補の検証が完了し、確定した指摘がなければ「指摘なし」と書く。未完了があれば、その範囲を明記して報告する。

結果の受け渡しと完了判定にはホストの標準機能を使う。共有ファイルが必要なら、親・レビュー担当・検証担当から参照できることを確認し、受け渡しが終わるまで保持する。対象を書き換える再現は一時領域で行い、後片付けでは自分が作成・変更したものだけを戻す。ユーザーや別担当の変更は戻さない。
