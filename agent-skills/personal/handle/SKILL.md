# handle

実装タスクの回し方。レビューの観点は既存 skill に任せ、この skill は順序と停止条件だけを持つ。

ARGUMENTS に GitHub issue 番号があれば、その issue（本文とコメント）を対象タスクとする。

## 1. 計画

計画には次を書く。

- 自分で決めた仮定 — コード・慣習・docs から判断したもの
- 変えないもの
- 完了したと言うための検証方法

プロダクトの挙動、スコープ境界と非目標、エラーやエッジケースの扱い、データの移行・互換性 — 手元の文脈から推測できない判断が残っているなら、仮定で埋めずに聞く。そのまま聞くか grilling で詰めるかは、聞く前に選ばせる。

issue 起点なら、確定した計画を issue 本文に反映してから実装に入る。次にその issue を読む人（無人セッションを含む）が計画を再構築せずに済む状態にする。

## 2. 実装

計画の範囲だけを実装する。計画に無い変更が必要になったら、やる前に言う。

## 3. 検証

変更面に応じた検証を実際に走らせ、何を走らせて何が通ったかを報告する。走らせられないものは理由を言う。走っていない検証を「たぶん通る」で埋めない。

## 4. 独立レビュー

fresh subagent に実行させる。日常は /code-review high、徹底時は deep-review。

- 差分は subagent 自身に取得させる。対象の指定（未コミット差分、HEAD からの差分など）だけを渡し、差分の切り出しを実装側でしない
- 実装意図・弁明・「ここは意図的」を渡さない

## 5. 収束

検証を通った指摘は握りつぶさず、提示で止めずに main セッションで直す。直したら再レビューし、指摘が無くなったら終える。

往復は main セッションが数えて4ラウンドを上限とし、達したら残った指摘と経緯を添えて人間に判断を返す。issue 起点ならその内容を issue にコメントする。
